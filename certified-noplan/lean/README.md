# CnpVerify — a Lean 4 checker for certified-noplan certificates

`lake exe cnp-verify <cert.json>` re-checks a disconnection certificate (SPEC §4) in exact
rational arithmetic and prints `PROOF …` (exit code 0) or `REJECT [code] reason` (exit code 1).
It is a port of `src/cnp/verify.py`, which remains the specification and is untouched.

**Status (L4): executable, proved, and — on one shipped scene — evaluated by the kernel.** The
checker runs and agrees with `verify.py`; the 19 theorems stated in L1 are proved
([PROOF-OBLIGATIONS.md](PROOF-OBLIGATIONS.md)), `lake build` reports no `sorry`; and for the
certificate `scenes/wall/k3.cert.json` the hypothesis `check c = true` is itself a theorem,
obtained by evaluation in the Lean kernel, so that the disconnection of that scene is a theorem
of Lean/Mathlib ([Certificates as Lean terms](#certificates-as-lean-terms--certs-l4)). The main
statement, `soundness_ref` (`CnpVerify/Soundness.lean`):

```lean
theorem soundness_ref (c : Certificate) :
    check c = true →
      ¬ ∃ γ : C(unitInterval, Fin c.n → ℝ),
          (∀ t, γ t ∈ c.box.toSet) ∧ γ 0 = vecR c.sStart ∧ γ 1 = vecR c.sGoal
            ∧ ∀ t, CollisionFreeRef c (γ t)
```

If the checker accepts a certificate, no continuous path inside the joint box joins the start to
the goal while the certified body, moved by real rigid motions along the declared chain, stays
out of every obstacle. The proofs are about the executable code as it was delivered in L1: it
has not been modified. **What this does and does not establish is spelled out in
[Trust base](#trust-base) below — read it before quoting the theorem.**

| `CnpVerify/Soundness.lean` | `CollisionFree`, `CollisionFreeRef`; C1–C4; `soundness`, `soundness_ref` | Mathlib |

The executable core imports nothing but core Lean, so the binary does not link Mathlib; the
specification layer imports the core and Mathlib. This is why the real-valued `eval` and the
statements sit in `Spec/` files next to the modules they are about, rather than inside them.

A second library, `Certs/` (not a default target), holds shipped certificates written as Lean
terms and the statements obtained by evaluating `check` on them — see
[below](#certificates-as-lean-terms--certs-l4).

## Build and run

Lean and Mathlib are pinned (`lean-toolchain`, `lake-manifest.json`). With
[elan](https://github.com/leanprover/elan) installed:

```
cd lean
lake exe cache get        # prebuilt Mathlib (several GB); only needed for the Spec layer
lake build                # executable + library with all the proofs (no `sorry`, no warning)
lake exe cnp-verify ../scenes/S6_iiwa_real_shelf.cert.json
```

`lake build cnp-verify` alone builds the executable in a few seconds and needs no Mathlib cache.
Options: `--json` (one JSON object: verdict, reason code, leaf and face index, time) and
`--dump` (print the certificate as parsed).

`lake build Certs` re-checks the per-scene theorems (several minutes and about 6 GB of memory:
the kernel evaluates the checker). From `certified-noplan/`: `make lean-certs` (generated files
up to date, `lake build Certs`, parser's object = term, axiom audit), `make lean-parity`
(agreement with `verify.py`), `make lean-kernel-bench` (the measurements of the table below).
The same gates run in CI (`.github/workflows/lean.yml`).

## Certificates as Lean terms — `Certs/` (L4)

`soundness_ref` is about the Lean TERM `check`; `cnp-verify` is what the compiler makes of it.
`Certs/` removes that gap for one shipped certificate and measures how far the others are.

| file | content | imports |
|---|---|---|
| `Certs/WallK3.lean`, `Certs/S3ShoulderElbow.lean`, `Certs/S6IiwaRealShelf.lean` | GENERATED by `scripts/cert_to_lean.py`: the JSON certificate as a term `… : Certificate` | core Lean |
| `Certs/Staged.lean` | `check c = true` from its stages (`check_of_stages`, `checkLeaf_collision_of`, `checkLeaf_outside_of`) | core Lean |
| `Certs/WallK3Kernel.lean` | GENERATED by `CertStages.lean`: `wallK3_proof : check wallK3 = true`, 34 evaluations `by decide +kernel` | core Lean |
| `Certs/Disconnected.lean` | `wallK3_disconnected` (S1 form), `wallK3_disconnected_ref` (S2 form) | Mathlib |
| `Certs/Native.lean`, `Certs/DisconnectedNative.lean` | the same route through `native_decide`, for the three certificates — FOR COMPARISON, one axiom more | core Lean / Mathlib |
| `CertTermCheck.lean` | control script: the object `Certificate.ofJson` reads from the JSON file equals the generated term | — |
| `CertStages.lean` | generator of the staged proof | — |

```lean
theorem wallK3_disconnected_ref :
    ¬ ∃ γ : C(unitInterval, Fin wallK3.n → ℝ),
        (∀ t, γ t ∈ wallK3.box.toSet) ∧ γ 0 = vecR wallK3.sStart ∧ γ 1 = vecR wallK3.sGoal
          ∧ ∀ t, CollisionFreeRef wallK3 (γ t) :=
  soundness_ref wallK3 wallK3_proof
```

`#print axioms wallK3_disconnected_ref`: `propext`, `Classical.choice`, `Quot.sound`. For this
scene the disconnection is a theorem of Lean/Mathlib: neither the compiler, nor the binary, nor
the JSON parser is involved. What remains to be read is in [Trust base](#trust-base).

**How `check wallK3 = true` is proved, and why not in one line.** Measured by
`scripts/lean_kernel_bench.py`, one process per attempt, killed beyond 9 GiB of resident memory
(1 GiB = 2³⁰ bytes) or a time limit never reached. Archived runs, under
`benchmarks/results/`: `20261010T163223Z` (k3 and S3), `20261010T171636Z` (S6),
`20261010T172639Z` (array operations). Machine: Apple M4, 24 GB, **not quiet** (load average 4
to 11 — a game was running on two of the ten cores): orders of magnitude are safe, the last
digit is not; `make lean-kernel-bench` replays everything.

| certificate | n | leaves (collision / outside) | body vertices | `by decide` | `by decide +kernel`, one evaluation | staged kernel proof | `by native_decide` (one axiom more) |
|---|---|---|---|---|---|---|---|
| `scenes/wall/k3.cert.json` | 3 | 2 (2 / 0) | 2 | FAIL at once (stuck on `Rat.blt 0 c.delta`) | FAIL — killed above 9 GiB after 53 s | **proved** — 34 stages, 277–359 s for the file (three runs), peak 5.6 GiB | 2.6 s (evaluation 0.14 s) |
| `scenes/S3_shoulder_elbow.cert.json` | 4 | 8 (4 / 4) | 2 | FAIL at once (stuck on `Rat.blt 0 c.delta`) | FAIL — killed above 9 GiB after 51 s | FAIL — three kinds of stage each exceed 9 GiB: kinematics (after 50 s), witness numerator (53 s), one face (41 s); an outside leaf passes (9 s, 2.2 GiB) | 1.1 s (evaluation 0.19 s) |
| `scenes/S6_iiwa_real_shelf.cert.json` | 7 | 2 (2 / 0) | 40 | FAIL at once (stuck on `Rat.blt 0 c.delta`) | FAIL — killed above 9 GiB after 48 s | FAIL — the staged proof cannot even be written: its literal `G` (262 440 coefficients) does not get through the elaborator, and stages that need no literal already exceed 9 GiB (`δ² − φ²` alone, after 48 s; `Σλ ≡ 1`; `λ_k ≥ 0`); the four global checks pass | 26.3 s (evaluation 24.00 s) |

* **`by decide`** fails at once, on every certificate, and no option changes that: the
  elaborator cannot reduce the `Decidable` instance because core `Rat.mul`, `Rat.inv`, `Rat.add`,
  `Rat.sub` are `@[irreducible]` (`Init/Data/Rat/Basic.lean`) — it is stuck on the first test of
  the checker, `δ > 0` (`Rat.blt 0 c.delta`; `decide` cannot prove `¬ (1 : Rat) / 10 ≤ 0`). This
  is a transparency block, not a resource limit: `maxRecDepth` and `maxHeartbeats` are not what
  stops it.
* **`by decide +kernel`** hands the evaluation to the kernel, which ignores reducibility
  attributes. In ONE evaluation it exhausts memory even on the smallest certificate: the
  kernel has no arrays — an `Array` is a list there, `set!` and indexing are linear, and the
  combinators the checker is written with are quadratic (on 125 entries, the size of a degree-4 tensor in 3 variables: `foldl` 0.79 s, `all` 0.84 s, `==` 1.56 s; on 625 entries, the size for 4 variables: 22 s, 21 s, 45 s) — and the memory of an
  evaluation is only released when the declaration is done.
* **Staged**: the same evaluation cut into independent kernel evaluations, each with its own
  memory — the four global checks, the kinematics `c.geometry` against a literal, `δ² − φ²`
  against a literal, and per collision leaf the witness numerator against a literal, the tests
  on `λ`, and ONE evaluation per obstacle face. `Certs/Staged.lean` proves that these stages
  imply `check c = true` (the converse of the unpacking lemmas of `Soundness.lean`). The
  literals are computed by compiled code and are NOT trusted: each is introduced by an equation
  the kernel checks by evaluating the other side. For `wallK3`: 34 stages; the kinematics stage is the heaviest in memory (37 s, 5.6 GiB), each of the 12 face stages takes 18 to 28 s and 3.3 to 4.0 GiB, the two witness stages 11 and 13 s; the file builds in 277 to 359 s (three runs under load).
* **It does not carry over to the other certificates as is.** On the 4-DOF certificate three
  kinds of stage each exceed 9 GiB taken alone, on literal inputs: the kinematics, the witness
  numerator, and ONE face — a single Bernstein test on 5⁴ = 625 coefficients; cutting finer
  does not split that one. On the 7-DOF flagship a single polynomial product (`δ² − φ²`)
  exceeds 9 GiB, and the intermediate values cannot even be written as a term within default
  limits (262 440 coefficients for the kinematics). The cause is the quadratic cost above.
  Carrying the flagship to the status of `wall/k3` would take a twin of the checker written
  for the kernel and PROVED equal to `check`; this has not been attempted.
* **`by native_decide`** compiles the term and runs it (here: the IR interpreter), then ADDS AN
  AXIOM stating the result — in Lean 4.34 one fresh axiom per use,
  `<theorem>._native.native_decide.ax_…` (`Lean/Meta/Native.lean`). It is fast on the three
  certificates, and it is exactly the trust in the compiler and run-time that the kernel route
  avoids: `scripts/lean_axioms.py` fails if a statement meant to be kernel-checked depends on
  such an axiom, and fails if a `…_native` statement does not.

**The term is the certificate.** `scripts/cert_to_lean.py` and `Certificate.ofJson` are two
independent readers of the JSON file; `CertTermCheck.lean` checks that they produce the same
object, field for field, on the three certificates, and `lean/check_certs.sh` checks that this
comparison fails when one number of the file is changed. This is a run-time check: the JSON
parser cannot be evaluated in the kernel (`Lean.Json.parse` is `partial`). It is also not
needed by `wallK3_disconnected_ref`, whose statement mentions the term only.

## Trust base

What one relies on when taking a `PROOF` printed by `cnp-verify` as a proof — and, at the end,
what is left of it for a per-scene theorem such as `wallK3_disconnected_ref`.

### Proved — checked by the Lean kernel

* **S2 `soundness_ref`** (above) and **S1 `soundness`** (the same statement on the polynomial
  pair `(N, D)` the checker computes), from: the tensor arithmetic computes the polynomial
  operations it claims (T1–T7); non-negative Bernstein coefficients imply non-negativity on the
  box (B0, B1); an accepted tiling covers the box (C1); an accepted `outside` leaf has
  `|φ| ≥ δ` on its cell (C2); an accepted `collision` leaf is in collision wherever `|φ| ≤ δ` on
  its cell (C3); the common denominator is positive (K1); the polynomial kinematics `N/D` IS the
  reference kinematics (K2, C4); the rational parametrisation `s = tan (q/2)` gives the rotation
  of angle `q` (K3), and Rodrigues' matrix is a rotation for a unit axis (K4).
* `#print axioms soundness` and `#print axioms soundness_ref`: `propext`, `Classical.choice`,
  `Quot.sound` — the three standard axioms, nothing else.
* Not among the 19, also proved: `check_eq_true_iff` (`check c = true` iff the sequence of
  checks `checkE c` succeeds, which is what the executable reports);
  `linkPose_rot_mem_specialOrthogonal` (under the kinematic check, the rotation part of the
  reference pose is in `SO(3)`); `skewR_mulVec`, `rodrigues_mulVec` (the reference rotation is
  `v ↦ v + sin · a × v + (1 - cos) · a × (a × v)`, with Mathlib's cross product).

### Defined — to be read

A proof shows that the checker agrees with the definitions the statement is written with; it
does not show that these definitions say what a roboticist means. They are short, contain no
polynomial and do not mention the checker. For `soundness_ref`:

| definition | file | what it says |
|---|---|---|
| `Certificate`, `Joint`, `Face`, `Obstacle`, `Vec3`, `Box` | `Certificate.lean`, `Kinematics.lean`, `Bernstein.lean` | the data. The statement reads `n`, `chain`, `bodyLink`, `hull`, `obstacles`, `box`, `sStart`, `sGoal` only: `φ`, `δ`, the leaves and their multipliers are the material of the proof, not part of the claim |
| `Box.toSet` | `Spec/Bernstein.lean` | `{x \| ∀ i, loᵢ ≤ xᵢ ≤ hiᵢ}` |
| `vecR` | `Spec/Kinematics.lean` | a rational vector seen in `ℝᵐ` |
| `Obstacle.toSet` | `Soundness.lean` | `{y ∈ ℝ³ \| ∀ faces, aᵀ y ≤ b}` (closed) |
| `CollisionFreeRef` | `Soundness.lean` | for every obstacle, the convex hull of the moved body vertices is disjoint from it |
| `Rigid`, `Rigid.apply`, `Rigid.comp` | `Spec/Kinematics.lean` | `y ↦ R y + t` and composition |
| `skew`, `skewR`, `rodrigues` | `Kinematics.lean`, `Spec/Kinematics.lean` | `K = [a]×` and `I + sin · K + (1 - cos) · K²` |
| `Joint.rotation` | `Spec/Kinematics.lean` | unlocked joint: `rodrigues` at `cos = (1-s²)/(1+s²)`, `sin = 2s/(1+s²)`; locked joint: at its rational `(cos, sin)` |
| `RefState`, `refStep`, `linkPose` | `Spec/Kinematics.lean` | `pose ← pose ∘ translate(offset) ∘ rotate`, along joints `0..link`; the `k`-th unlocked joint reads `s_k` |

plus Mathlib's `convexHull`, `Disjoint`, `C(unitInterval, ·)`, `Matrix` and `ℝ`. `soundness`
(S1) reads, instead of `linkPose`, the checker's own `bodyNumerators` / `bodyDenominator`
through `Tensor.eval` — which is why S2 is the statement to quote.

Things the statement says, and things it does not:

* It is a statement in **`s`-space** (`s = tan (q/2)`, as in the certificate): the path, the box,
  the start and the goal are in `s`. The translation of a path in joint angles (inside
  `(-π, π)`) into a path in `s` is not formalised. The field `q_star` does not occur in the
  statement; the checker requires it to be zero, which is what makes `s = tan (q/2)` the right
  reading of the certificate.
* It is about **one body and the listed obstacles**, exact polytopes, static. A path that is
  collision-free for the whole robot is collision-free for that body, so the conclusion
  extends to the robot; the converse is not claimed.
* **Touching is a collision** (obstacles are closed sets).
* If the start or the goal is outside the box, the statement is vacuously true.
* It is **soundness only**. Nothing says the checker accepts every true disconnection, nor
  anything about the program that produced the certificate.

### Outside the statement — trusted, not proved

* **Parsing.** The theorem is about a value of type `Certificate`. `Certificate.ofJson` (JSON
  file → `Certificate`) is ordinary unverified code; `cnp-verify --dump` prints the object that
  was actually checked. That the certificate describes the intended scene and robot (YAML
  scene, URDF) is not a matter for this checker at all.
* **Compilation and run time.** The theorem is about `check` as a Lean term. The binary is what
  the Lean compiler and the C toolchain make of it: the compiler, the run-time arithmetic
  (`Nat`, `Int`, `Rat` on GMP), `Array` and the `@[extern]` / `@[implemented_by]` replacements
  of core library functions are trusted.
* **`Main.lean`**: file reading and printing. It prints `PROOF` exactly when `checkE c`
  succeeds.
* **The proof checker itself**: the Lean 4.34.1 kernel, and Mathlib `v4.34.1` for the
  definitions of `ℝ`, continuity, convex hulls, matrices.

Agreement with `verify.py` is **measured**, not proved (section "Parity with `verify.py`").

### Per-scene theorems — what is left to trust (L4)

For `wallK3_disconnected` and `wallK3_disconnected_ref` (`Certs/Disconnected.lean`) the
hypothesis `check wallK3 = true` is proved by kernel evaluation (`Certs/WallK3Kernel.lean`), so
two items of the list above DROP OUT:

* **no compiler, no run time, no binary, no `Main.lean`**: nothing was compiled to obtain the
  statement (`#print axioms`: the three standard axioms; a `native_decide` proof would show a
  fourth);
* **no parser**: the statement is about the term `wallK3`, written out in `Certs/WallK3.lean`.

What remains: the Lean kernel and Mathlib; the reference definitions of the table above; and
reading the term `wallK3` — for the `_ref` statement, its fields `n`, `chain`, `bodyLink`,
`hull`, `obstacles`, `box`, `sStart`, `sGoal` (3 joints, 2 body vertices, one obstacle of
6 faces, a box, two points). That this term is the content of `scenes/wall/k3.cert.json` is
checked at run time (`CertTermCheck.lean`), not proved, and that the certificate describes the
intended scene is, as before, not a matter for the checker.

For the other shipped certificates the kernel evaluation does not fit in memory (table of the
section "Certificates as Lean terms"): their status is unchanged — a `PROOF` printed by the
binary, under the trust base above. The statements of `Certs/DisconnectedNative.lean` depend on
a `native_decide` axiom and are theorems MODULO THE COMPILER; they must be quoted as such.

## Parity with `verify.py`

`make lean-parity` (from `certified-noplan/`) builds everything, exports the adversarial corpus
from the Python test-suite mutations (`scripts/export_mutations.py`) and compares both verifiers
(`scripts/lean_parity.py`) on every shipped certificate, on the corpus (verdict and reason), and
on a seeded differential fuzz (verdict).

## Where the Lean checker is stricter than `verify.py`

`verify.py` reads the JSON lazily while checking; the Lean checker parses the whole document
into a typed `Certificate` first. On well-formed certificates the two agree. On ill-formed
ones the Lean checker rejects (`malformed`) inputs that `verify.py` accepts or aborts on:

* a number written as a non-integer JSON number, a JSON boolean, or with non-ASCII digits
  (the schema says numbers are strings; `Fraction` happens to accept those);
* an unparsable value in a field `verify.py` never reads (an obstacle no leaf refers to, the
  `cos`/`sin` of a locked joint downstream of the body);
* `start_s` / `goal_s` shorter than `n`, a box or a cell with more than `n` intervals;
* a negative `body.link`, a lock on a joint that does not exist, a duplicated exponent key.

For a certificate with several defects the *reason* reported can differ (the parser runs
before the checks). None of these makes the Lean checker accept something `verify.py` rejects.
